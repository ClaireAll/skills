# 禁用与不可用功能规范

## 处理方式

| 场景 | 处理方式 | 反馈要求 |
| --- | --- | --- |
| 当前上下文不存在该能力 | 不显示 | 不增加无意义入口 |
| 固定角色权限长期不可用 | 不显示 | 不展示永远不能使用的菜单 |
| 项目或对象动态权限受限 | 灰化禁用 + 悬浮提示 | 保持结构并说明限制 |
| 未选择、未填写、未勾选 | 灰化禁用 + 悬浮提示 | 说明需要先完成的条件 |
| 原因复杂，用户难以理解 | 保持可点击 + 点击后提示 | 解释原因并给出下一步 |
| 需要后端或多层判断 | 保持可点击 + 点击后判断 | 先加载，完成后执行或反馈 |

## 判断顺序

1. 当前上下文是否存在该能力；不存在时隐藏。
2. 是否是用户长期固定无权限；是则隐藏。
3. 是否是可以提前确定的简单临时条件；是则禁用并提供悬浮提示。
4. 是否需要多条件、后端或点击后才能确认；是则保持可点击并在点击后反馈。

无法判断归类时标记待确认，不自行假定隐藏或禁用。

## 实现要求

- 禁用不仅是变灰，还要阻止原操作，并保证原因提示可触达。
- 原生 disabled 无法 hover 时，使用项目已有的可悬浮容器或组件承载提示。
- 禁用原因 Tooltip 不是错误 Tooltip：按钮与文本/列表分别遵循 `tooltip-validation.md`，不能仅因 disabled 使用错误色。
- “保持可点击 + 提示”不能静默无响应；复杂判断期间展示加载状态。
- 提示内容解释当前原因；规范要求下一步指引时，给出可执行路径。

## 审查证据

- 上下文切换后，不属于当前逻辑的入口是否消失。
- 固定角色无权限与动态权限是否分开处理。
- 前置条件变化时，禁用状态和原因提示是否同步更新。
- 多条件失败时，点击后是否说明实际原因。
- 后端判断期间是否有加载状态，失败后是否给出下一步。
- 禁用提示是否可触发，是否被误用成错误色。
