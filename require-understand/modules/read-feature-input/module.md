# 读懂功能/交互文档输入(通用规则)

这是一套**可复用的输入读取规则**,被其它 skill 的「读输入」步骤引用(也能单独用于「帮我读懂这份需求材料」)。

**核心边界:本 skill 只负责把各种形态的输入读全、读对、读懂,不规定读完之后怎么用。** 要不要把理解落成中间产物(报告 / 清单 / 直接进入下一步),由**调用方 skill 决定**——本 skill 既不强加,也不禁止。

## 1 · 识别输入形态

输入可能是下面任意一种,或几种混合(例如"功能看这个飞书链接,交互看这个 figma"):

- 飞书文档链接
- Figma 链接
- 本地 md / 其它文件路径
- 用户直接打字的一段功能描述
- 以上的混合

先判明有哪些来源,再逐个读;**别只读第一个就动手**。

## 2 · 各来源的正确读法

### 飞书文档

- 用 `mcp__feishu-doc__fetch-doc`,直接传 URL。
- 文档里若引用了画板(脑图/流程图)或图片且影响理解,用 `mcp__feishu-doc__fetch-file` 取图看(画板传 `type=whiteboard`)。

### Figma(纪律最严,最容易漏读)

- **必须走 Figma MCP**(`get_design_context` / `get_screenshot` / `get_metadata` / `get_figma_data`)。调用前先看工具 schema 按参数传。
- **禁止用 WebFetch / 裸 HTTP 抓 Figma 网页**当作"已读交互稿"——抓不到稳定节点树和标注,必漏交互覆盖。
- 从 URL 解析 `fileKey`;带 `node-id` 时把 `1-4` 这类格式转成 API 用的 `1:4`;没带节点先拉整文件再按需收窄。
- **务必逐个读画板里的「备注」框(name 含「备注」的 FRAME/INSTANCE)和紧贴画板的旁注 TEXT**——入口、置灰/选中、Tooltip、校验时机与文案、toast、复制粘贴规则、标红与报错策略、与 PRD 的冲突点等**验收规则常藏在备注里**,只看组件 demo 会漏。
- **画板旁边的规格卡 / 标注卡是一等需求来源,不是装饰**:任何以说明、规格、注释形式呈现的结构化信息,都要作为验收规则读取;只看画板主体 UI 截图会漏规则。
- 规格卡与多个对象相邻时,必须建立其归属关系;归属不清就标 `【待确认:Figma 标注归属不明】`,不要把旁边的大段标注直接忽略。
- **排版量与色值要抓成设计变量名,不是抄数值**:字号 / 行高 / 控件高度 / 间距 / 圆角 / 各状态色值在设计稿里都由设计变量定义,用 `get_variable_defs` 取变量名。下游断言锚在变量名上 —— 同一个变量在不同主题作用域下取值不同,抄下来的 hex / px 换个主题就不成立。数值只作对照记录,并注明是哪个作用域下的取值。
- **Figma 图层/节点编号只用于你内部分析**,把内容映射进下游产物时**一律语义化指称**(如「画板备注:导出与异常」),**禁止把 `210:31749`、「备注315」这类编号写进下游产物正文**(用户 URL 里原生的 `node-id=` 参数除外)。
- MCP 真的不可用(多次失败 / 未鉴权 / 无文件权限)时:在对话写明原因和已试步骤,相关交互内容标 `【待确认:Figma MCP 不可用】`,**禁止**用"未能自动读取 Figma"草草收尾。

### 本地 md / 其它文件

- 用 `Read` 读取路径指向的文件。

### 一段文字描述

- 用户直接打字的需求,直接用,不用去找文件。

## 3 · 混合来源对齐

- 把**所有**给到的来源都读完再动手,别漏掉其中一个。
- 来源之间冲突时:优先采用结构化程度更高、结论更明确、更新更晚的;消不掉的冲突,把该点标 `【待确认】` 交给下游处理。

## 4 · 读懂什么(读取重点)

读的时候主动把这些抓全,作为"读到位"的检查项,便于调用方直接使用:

- 功能点与业务规则、状态流转、权限规则
- 交互行为:入口、置灰/选中态、校验时机与文案、toast、标红与报错、显隐流转、**状态之间能否叠加**(报错的元素被选中时是什么表现、禁用的元素被悬浮时是什么表现);材料把状态写成并排的几项时,默认它们互斥是常见误读,读不出叠加口径就标 `【待确认】`
- **视觉与排版规格**,分两级抓:**元素级** —— 本次新增 / 改造的标签、徽标、图标,逐状态的底色 / 边框 / 文字色 / 圆角 / 内边距;**容器级** —— 承载它们的面板、弹窗、抽屉、折叠区**自身**的内容区字号、配置行的标签与控件如何对齐、控件高度、页脚按钮尺寸、行间距。**容器级最容易整档漏读**:需求文档只说面板里有哪些配置项,设计稿只呈现排好版的成品,两边都不会把「这个面板用小一号字、按钮用小尺寸」写成一句话,得从稿子上量、从设计变量里读
- 数据/字段线索:涉及的字段类型、数据来源、空值/异常/边界提示
- 初始化与状态规则:默认、初始、状态差异、兼容与降级口径
- 约束 / 硬规则 / 特殊要求
- 是否声明了升级兼容、移动端
- **待确认点与矛盾点**(含需求里的 Q 编号、与 PRD 冲突处)

## 5 · 信息不足就先问

如果关键交互、规则或边界在所有来源里都说不清,**先问用户一两个具体问题**,而不是猜着补。把理解建立在读到的内容上,读不到的就标 `【待确认】`,别硬编。
