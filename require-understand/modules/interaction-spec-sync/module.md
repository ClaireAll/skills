# 交互规格与代码对齐

本模块只在 `read-feature-input` 已读完所有需求来源后使用。目标是说明当前文档与当前代码的关系，不是用代码自动判定产品决策对错，也不修改业务源码。

## 输入与边界

开始前确认以下信息：

- 已读取的需求或交互来源：飞书、Figma、本地文件或其组合。
- 需要比对的源码目录或文件范围；没有范围时，只问用户一个聚焦问题。
- 若用户要求写回，目标飞书文档或 wiki 页面及其可编辑权限。

只扫描用户指定范围内与交互相关的入口、组件、状态、校验、文案、权限、异常分支和测试。不要因为一次对齐任务扩展为全仓库审计。

## 建立对照

先从已读材料提取语义化对照项，再在源码中查证每一项。每个对照项至少覆盖：入口、默认或初始状态、用户操作、状态变化、校验或异常反馈、最终结果。

查代码时先用 `rg` 收窄候选文件，再读取必要的实现、类型、接口、测试和配置。代码无法证明的事实不能补成结论。

将结果归为下列四类：

| 分类 | 含义 | 处理 |
| --- | --- | --- |
| 一致 | 文档与当前代码表达同一行为 | 不额外插入说明。 |
| 文档与代码不一致 | 两者对同一行为给出不同结果 | 记录双方现状，不擅自改代码或改写原规则。 |
| 文档遗漏 | 指定范围内的代码已经实现可感知行为，文档没有覆盖 | 补充简洁、可验收的交互说明。 |
| 待确认 | 来源缺失、实现含糊，或无法判断哪一方应为准 | 说明缺少什么证据并交由用户决定。 |

## 输出与写回

默认只输出只读审计：按文档小节列出对照结果、相关源码路径和待确认项。不要在未获明确写入请求时修改飞书页面。

用户明确要求同步飞书文档时，先读取 `feishu-doc-writer`，并遵守其写入与回读流程。所有内容必须插入对应的小节或小点附近，不能集中追加到文末的“差异汇总”。保留原始文档内容，不把代码现状静默改写成产品规则。

使用下列标记，且标记文本本身必须表达语义，不能只依赖颜色：

- 橙色：`【与当前代码不一致】`，简述文档描述、当前代码行为和需要确认的决策。
- 绿色：`【补充：当前代码已实现】`，补齐遗漏的入口、交互、状态或反馈规则。
- 普通文本：`【待确认】`，注明无法读取的来源或仍缺少的产品口径。

当小节包含视觉状态、控件状态或操作路径，并且有可核验的 Figma 画板或运行页面时，在对应小点下附一张信息充分的截图及简短图注。不要为凑图重复插入无新增信息的截图；Figma 节点编号不得出现在面向用户的文档正文。

只有用户明确要求润色新增文案时，才加载 `human-writing`。普通同步应保持准确、简短和可验收，不扩写营销式说明。

## 交付检查

- 对照项覆盖所有已读来源中与指定代码范围相关的交互规则。
- 橙色和绿色内容均位于正确的小节，不存在集中附录替代就地说明。
- 每一项矛盾都同时说明“文档说什么”和“代码当前做什么”。
- 无写权限、MCP 鉴权失败或来源无法读取时，只交付定位明确的本地草稿，不声称已同步。
- 不修改业务源码、不创建提交或 PR，除非用户另有明确要求。
