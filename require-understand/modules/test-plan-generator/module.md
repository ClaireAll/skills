# 测试计划生成器

把一份「需求/交互说明」转成一份**可评审、可据此直接写用例**的测试计划,核心产物是一张飞书原生脑图(测试场景骨架),再附一份场景完善性自检清单,最后回填到飞书指定目录待人工评审。

## 这个 skill 在解决什么

测试计划最容易写废的两种方式:一是把功能文档/交互稿的文字**照搬**成一条条"测试点",评审时看不出场景骨架;二是**漏场景**——异常、交叉、兼容这些维度想不全。本 skill 用两件事对抗:(1) 用 mermaid 脑图强制把内容组织成**场景树**而非平铺测试点;(2) 用团队的「场景完善性」清单作为**生成时的覆盖驱动**,逐维度主动找场景,而不是写完才回头检查。

## 产物结构

每份测试计划是一篇飞书文档,固定六节(详见 `references/feishu-output.md` 的完整模板):

1. **功能概要** — 最多 3 条,每条 1 句,只讲「功能是什么」(做什么、对谁生效、解决什么问题);不堆交互/兼容/边界/性能细节,那些进脑图
2. **任务链接** — 飞书任务链接(没有就写「待补充」)
3. **参考资料** — 功能/交互/开发/视觉文档来源(有哪个列哪个)
4. **计划概览** — 一张 mermaid `mindmap`,即测试场景骨架(**核心**)
5. **场景完善性自检** — checkbox 清单,逐条标注覆盖情况
6. **审核/评审人员** — 一条「测试计划审核」待办,@当前登录用户,带到点提醒(回填当天 +2 天的 18:00,提醒接收人 = 当前登录用户)

## 工作流

### 1 · 收集并读懂输入

输入可能是飞书文档 / Figma / 本地 md / 用户直接打字的一段功能描述,或几种混合。

**REQUIRED INPUT MODULE:** 先读 `../read-feature-input/module.md` 并按其执行:识别来源、各自正确读取(含 Figma 必走 MCP、读全画板备注/旁注、不泄漏节点编号)、混合来源对齐、信息不足先问。读懂后直接进入第 2 步。

### 2 · 拆成测试场景,而非测试点

围绕"用户/系统在什么情况下做什么、期望什么结果"来组织,目标是评审完能**照着往下拆测试用例**。判断标准:每个叶子节点应能直接对应一条或一组用例,而不是文档原文的复述。

- 先抽出**功能主流程场景**(正常路径,按用户操作链条走)。
- 再补**配置/参数维度**(不同设置、不同数据形态下的表现)。
- 叶子写到"具体可验证的点"(例:不是"选中置顶",而是"多选时已选项按选中先后顺序置顶")。

先判**模块处理类型**再定策略:全新增→完整铺场景;改造→聚焦变更点回归 + 保留功能正向流;下线→只生成 1~2 条「入口不可见/不可访问」轻量校验;复用前版本→搬入旧测试点适配差异。系统提取场景的专业方法(等价类/边界值/状态迁移/错误推测/正交/变更回归等)见 `references/analysis-methods.md`,挑适用的用、至少 3 种。

### 3 · 用「场景完善性」驱动覆盖

这是质量的核心。生成场景树时,拿下面每一条**主动去想**有没有对应场景,能落就落进脑图对应分支,落不下的记下"不涉及 + 原因"留到第 5 节:

**总要想的:**

- 功能文档、交互文档中的内容是否都有覆盖
- 团队评审时提出的问题、场景是否有覆盖(包括后期群里讨论的场景)
- 是否考虑了**交叉场景**(对相关功能的影响)
- 是否考虑**异常场景**(空值、超长、非法输入、网络/加载失败、并发冲突)
- 是否考虑了**国际化**(涉及文案/多语言才需要)

**按需判断的(不是每个需求都涉及,别反射式地加):**

- **升级兼容** —— 结合**功能文档**(有没有改动已有结构/默认值/数据格式)和**项目现状**(是否存在会受影响的老模板/老数据)判断。涉及才建「升级兼容」分支,并关注是否需提设计风险确认;不涉及就不建分支,第 5 节注明判断依据。
- **移动端** —— 结合**功能文档**(有没有声明移动端)和**项目现状**(该功能/组件在本项目里到底有没有移动端实现)判断。duchamp 移动端是独立分叉,**判断不准就去代码里确认**(找该组件的 `.m.*` 移动变体、mobile 目录下有没有对应实现);有才建分支,没有就标不涉及。

适用的维度应在脑图里**显式成为一个分支**(如「异常场景」「升级兼容」),脑图本身就体现完善性,第 5 节的勾选才有据可查。不适用的维度别硬塞场景——第 5 节标明不涉及及依据即可。

**按需求类型补领域交叉维度**:判断本需求是否涉及**公式 / 分析组件(交叉表) / 导出**,或操作了**通用横切对象**(很长的名称、很多的字段、各类字段类型与空值异常数据、搜索、跨项目、依赖资源丢失等)。命中就读 `references/scenario-dimensions.md`,把对应领域清单补成脑图分支(如一级节点「导出交叉场景」「分析组件交叉场景」),逐项覆盖别合并成一条「导出正常」。不命中的领域别硬塞。

**三条落地纪律:**

- **性能/埋点不进脑图** —— 这是功能测试计划,需求里的性能、埋点、响应时延、稳定性默认不映射成脑图节点(要提就在第 5 节或对话一句「见性能/埋点专项」)。与功能行为绑定的(如「大量小计行仍展示正确层级」)只保留展示/计算正确性表述,去掉性能指标。
- **硬约束拆进业务模块叶子** —— 功能文档里的硬约束/特殊规则逐条落到**最相关模块的叶子场景**,别单独起「硬约束汇总」一级分支,也别和模块场景重复罗列;说不准或与 PRD 冲突的点,在叶子末尾标 `【待确认】`。
- **业务语言,非开发黑话** —— 读者是产品 / 测试,脑图节点与场景描述一律写成业务话「(在什么情况下)做什么 → 期望什么结果」;**禁止出现**内部代号(B1/B2)、函数 / 文件名、`@tag`、cursor / 求解器 / 钳制 等实现术语。覆盖方式只说「自动化 / 模版自动化 / 逻辑单测」,不暴露内部机制(实现细节属 design.md,不进测试计划)。需要更具体时,可在脑图概览之外**再配一张「操作 → 预期结果」场景表**(脑图给一眼概览、表格给可照做的步骤),但表格也用业务措辞。**评审反馈「看不懂 / 太技术」时,先查是不是漏了这条。**

### 4 · 生成测试计划草稿(本地)

按 `references/feishu-output.md` 的模板拼出完整 markdown。重点:

- 第 4 节的 mermaid `mindmap` 是脑图来源——**节点文本、缩进、转义有硬规则,务必照 reference 写**(写错飞书渲染会失败)。
- 第 5 节按"该维度已在计划里有对应场景 → `[x]` + 一句话说在哪;本需求不涉及 → `[ ]` + 原因"逐条填。

### 5 · 本地审阅 → 确认后回填

**先把草稿完整贴给用户看**(markdown + 准备回填的目标目录),问一句"确认回填到飞书「AI生成待审核」吗?"。这是团队约定:改飞书前先出本地草稿待审,确认了再发。用户说"直接回填/可以"再执行第 6 步;用户提修改就改完再确认。

**审阅收尾顺手做一次自迭代反思**:用户加/改的场景,若是「以后出**任何**测试计划都该想到的维度」(而非这个需求特有),按下方「自迭代」提炼成规则,补进场景完善性清单或 `scenario-dimensions.md`,下次主动覆盖。

### 6 · 回填飞书

确认后,用 `mcp__feishu-doc__create-doc` 在目标 wiki 节点下**新建**一篇子文档(每次一篇,挂进待审目录)。参数、目标节点 token、以及**必须传真实换行不能传 `\n` 字面量**这条致命坑,全在 `references/feishu-output.md`。建完把 `doc_url` 回给用户。

## 关键参考

- `references/feishu-output.md` — 完整产物模板、mermaid mindmap 书写规则与飞书渲染坑、回填 API 参数与目标节点。**写第 4/6 步前必读。**
- `references/scenario-dimensions.md` — 按需求类型(通用横切 / 公式 / 分析组件 / 导出)补齐交叉场景的维度库。**第 3 步判断命中后读对应小节。**
- `references/analysis-methods.md` — 测试设计方法(等价类/边界值/状态迁移/错误推测/正交…)+ 模块处理类型策略 + 落地纪律展开。**第 2/3 步内部推理时参考。**

## 自迭代 —— 把评审暴露的缺口沉淀成维度

本 skill 的质量取决于第 3 步「场景完善性」清单和领域维度库够不够全。评审时**每暴露一类「没想到要问」的场景,都是清单的一个洞**;通用的洞要**提炼成维度写回 references**,下次主动覆盖 —— 这是计划生成器的自我增强。机制是一条内联反思回路,不另起文件、不起子 agent。

**① 触发**:第 5 步审阅时用户加/改了场景、或评审反复暴露某类场景没被想到。

**② 提炼**:先判这是「**任何**计划都该想到的通用维度」还是「这个需求特有」。**只有通用的**才提炼成规则(写「该想什么 + 为什么」,不写「上次漏了 X」的叙事;具体到可勾选的自检项 / 可套用的维度清单,不用「等」)。

**③ 归位(就近强化已有处)**:

| 缺口类型                                                     | 写到                                         |
| ------------------------------------------------------------ | -------------------------------------------- |
| 跨需求**总要想**的维度(如某类异常/交叉一直被漏)              | 第 3 步「场景完善性」清单加一条(module.md)   |
| 某**领域**(通用横切 / 公式 / 分析组件 / 导出…)的成套交叉场景 | `references/scenario-dimensions.md` 对应小节 |
| 缺的**测试设计方法** / 模块处理策略                          | `references/analysis-methods.md`             |
| 飞书模板 / mermaid 渲染 / 回填坑                             | `references/feishu-output.md`                |

**④ 写前先确认**:维度库改的是所有后续计划都吃的共享规范,且正逢有人审阅 —— **先把拟加的维度念给用户、确认后再落**,别静默改 skill。

**别记的**:**这份需求一次性的疏漏**(漏想了某个场景)—— 补进当份计划即可,**哪也不记**,只有同型缺口跨需求反复出现才升级成上面的通用维度;需求本身的口径/场景属该计划(及对接的 `design.md`)的常规内容,不是自迭代的记录动作。

> 边界:通用维度进 skill references(随仓分发);需求级细节进 `docs/`;都不进全局记忆。
