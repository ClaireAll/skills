# 测试设计方法 & 模块处理策略

供自查用例模式组织场景或源码审查筛选检查路径。这些是分析思路，不能保证发现所有未知问题，不要原样抄成检查口号。

## 一、先判模块处理类型,再定策略

- **全新增**:完整铺正向 / 逆向 / 边界 / 异常全套场景
- **改造**:聚焦变更点回归,兼顾保留功能的正向流
- **下线验证**:只生成 1~2 条「入口不可见 / 不可访问 / 越权拦截」轻量场景
- **复用前版本(规则无变化)**:把前版本测试点逻辑搬入,适配当前版本差异点后输出

## 二、测试设计方法(按实际风险选用)

- **等价类划分**:每个输入字段分**有效**等价类(合法输入)与**无效**等价类(空值、超长、格式错误、非法字符)
- **边界值**:数值取 min / min-1 / max / max+1 / 中间值;字符取空串 / 单字符 / 最大长度 / 超长 / 特殊字符
- **决策表**:多条件组合场景,理清条件依赖关系
- **场景法**:正向主流程 / 逆向异常操作 / 多功能组合场景 / 异常流(触发错误、失败的路径)
- **状态迁移**:列全状态节点、所有合法转换路径、应被阻止的非法转换
- **错误推测**:用户易错(忘开开关、超限输入)、系统易错(配置不生效、缓存未刷新、权限问题)、新旧版本兼容
- **正交实验**:多因子场景下减用例数但保覆盖度
- **变更专项回归**:识别需求里的显式变更标记([NEW] / [CHANGED] / 「变更前→变更后」/ Δ 编号),每个变更点 1 条专项,直接验证新行为已按描述生效
- **补充特殊维度**:
  - **权限**:有角色权限矩阵就逐行生成——每个「不可以」格有越权拦截、每个「可以」格有正向;无矩阵就枚举不同角色对同一功能的行为差异
  - **数据边界**:空列表、大量数据、特殊字符数据
  - **并发**:重复提交、同一链接多次使用等

## 三、落地纪律

- **硬约束 / 特殊规则**：逐条对应实际业务模块的代码路径或用例，不用一条宽泛场景代表多个独立规则。
- **性能 / 埋点 / 时延 / 稳定性**：未被要求时不自行执行专项测试；当前需求明确给出的指标仍需记录，缺运行证据时列为待验证，不擅自删掉或编造数值。
- **矛盾消除**：依据用户已确认决定、适用范围和生效证据判断；不能仅凭更新时间、格式或现有实现选择预期。没有裁决依据的点列 `Q`。
- **待确认项**：将具体问题关联到受影响规则、检查路径和用例；不把未决预期算成已确认覆盖。
