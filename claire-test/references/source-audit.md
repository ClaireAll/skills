# 只读源码审查与修改方案

默认交付是代码问题及供用户自行实施的方案。读取需求、源码和已有测试，不修源码，不运行页面，不生成测试脚本。

## 1. 明确依据与范围

- 复用已读取的资料；需要补读时使用 [本地需求输入模块](../../claire-require/modules/read-feature-input/module.md)。给原文规则稳定编号 `R`，实现路径编号 `C`，待确认项编号 `Q`。
- 需要明确的代码范围：目录、文件、PR、提交或比较基准。检查 staged/unstaged/untracked 状态，保留无关改动；不把所有脏文件或全仓库当作默认范围。
- 只有源码时，继续做可证明的实现与边界审查，明确“规格对照缺少需求依据”。只有文档且没有代码范围时，先整理规则并询问范围，不声称已经找到代码缺陷。
- 未读正文、图示和接口实现记为缺口。现有代码和测试不能单独证明业务预期；资料冲突按已确认决定及适用范围判断。

## 2. 复用完整规格对照插件

加载已安装的 `spec-to-code-compliance:spec-to-code-compliance`。本机插件根目录是 `D:/Claire/cache/codex-plugins/claire-page-testing/spec-to-code-compliance/2.0.2`；先检查实际文件可读，路径失效时按当前可用 Skill 定位，不猜另一个版本。

上游 `SKILL.md`、`workflows/spec-compliance.js`、`agents/spec-compliance-checker.md` 及其 resources 是规格判断的依据，不在这里复制一套判断标准。

**有上游工作流运行器时：**使用它传入代码范围、实际读取的规格文件及任务目录中的 `outDir`。核对 `notChecked`、`unverified`、`unreadableDocuments`；当前脚本默认检查 10 条、单次最多 30 条，大文档分批，不能只看第一批就宣布全量通过。

**Codex 没有该运行器时：**不要直接用 Node 执行这个依赖宿主 `agent/phase/budget` 等绑定的脚本。读取上游工作流和 checker 指令，用当前宿主的子代理工具执行同样的阶段：

1. 从已读规格拆出独立可核查要求，保留原文和来源；复合要求拆开，背景说明不升级为硬性验收。
2. 每项要求由独立 checker 上下文审查；让它读取上游 `agents/spec-compliance-checker.md`，将 `{baseDir}` 指向实际插件根目录，分析只写任务目录。复用上游工作流的记录字段和分析格式。
3. 对候选差异，用未参与发现的上下文分别复核代码执行路径和文档语义。验证者实际重读相关源码/原文，不能只接受 checker 的结论。
4. 对上游“未记载行为”反向检查单独记录；有未写入文档的行为不等于它一定是 bug。
5. 汇总原始判定、复核结果、证据和未覆盖项。记录缺失来源、不可用工具及失败阶段；验证者失败不能当作已确认，也不能无声丢弃可疑项。

这称为“按上游规则执行的 Codex 子代理适配”，不是“上游原生工作流已运行”。如果宿主没有子代理能力、调用失败，或连续等待仍没有返回结果，停止受影响阶段，不重复创建等价任务或无限重试；交付已有证据并明确缺少哪些独立检查，不声称完成该插件的完整流程。需要结束失败的子代理时，只关闭本次创建的任务。

## 3. 补查规格之外的边界

按 [边界检查表](boundaries.md) 选择实际适用的状态、数据和调用关系，必要时读取 [领域维度](scenario-dimensions.md)。重点跟踪输入、初始化、状态变更、请求、保存和回显，检查各调用方及共享实现，而非只看 diff。

用源码证明可达性和实际后果：空值/零值、权限直达、历史字段缺失、异常响应、请求倒序、取消与重开、重复操作、共享状态及关联旧功能。排除被类型、调用方、统一校验或状态约束阻止的情况。只因“没有测试”或“可以更优雅”不能作为已存在的 bug。

按需检索 `D:/Claire/memory/bug-fix.md` 的相关症状和模块；历史只用于选择检查路径，不等于本次已经复现。团队交互标准可按需读 `fx-ui` 的对应规则；通用正确性审查可复用 `ponytail:ponytail-review`，但不重复启动另一轮无关审查。

文档外候选也要做反证检查；交给已授权的独立验证上下文，或在没有该能力时注明只做了主上下文复核。

## 4. 输出问题及可实施方案

默认在对话中输出；用户要求文件时写到指定位置，未指定时使用 `D:/Claire/papers/<日期>_<任务>/code-review.md`，不覆盖已有任务结果。正式问题按影响排序，资料不足的候选单列待确认。

每个正式问题包含：

- **编号与影响**：稳定 `F` 编号、严重程度，解释用户可观察后果，避免把所有问题都升级为阻断。
- **位置与依据**：实际源码文件及行号、对应 `R/C`；没有文档依据的边界问题明确标为实现缺陷，不能冒充需求原文。
- **触发与行为**：可达的角色、初始状态、输入和操作，当前结果与已知预期；给出相关调用链和根因证据。
- **修改方案**：应改的文件/方法、共享层或调用方、最小修法、受影响消费者与兼容点。必要时给最小代码示例，但不落成产品补丁。
- **手动验证**：用户修改后应怎样验证正常、异常和关联回归；尚未执行的步骤明确写“待验证”。
- **证据等级**：源码已确认 / 最小运行验证 / 待实际页面确认。静态推导不能称为页面已复现。

结尾列规则与路径覆盖情况、未读来源、未检查项和未决产品规则。未发现问题只表示当前已检查范围没有发现，不代表保证无 bug。

整个流程中不改产品代码、不新建 test-id、不调用 BDD、不自动调用 `webapp-testing`。用户后续点名页面验证时再交给独立页面测试工具。
