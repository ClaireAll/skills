# 飞书文档生成规范

> 本规范用于指导 Codex / 文档生成助手输出适合直接写入飞书文档的 Markdown 内容。目标是让文档结构清晰、视觉友好、结论明确、便于协作和评审。

---

## 0. 使用方式

### 适用场景

当用户提出以下需求时，应优先按本规范生成飞书文档：

- “写飞书文档”
- “开发文档”
- “分享文档”
- “评审文档”
- “飞书 doc”
- “整理成飞书文档”
- “输出一份可以发给产品 / 设计 / 测试 / 领导看的文档”

### 推荐指令

```text
请根据当前任务，按照 docs/feishu-doc-style-guide.md 的规范，生成一份适合直接复制到飞书文档的 Markdown 文档。

要求：
1. 结论先行。
2. 可视化优先。
3. 避免大段文字。
4. 面向业务读者，少用技术黑话。
5. 不确定的信息标记为“待确认”，不要编造。
6. 直接输出 Markdown 正文。
```

### 工具建议

| 目标 | 推荐去向 | 工具 / Skill | 说明 |
|---|---|---|---|
| 协作、评论、@人、评审定稿 | 飞书文档 | `lark-cli` + `lark-doc` | 适合团队协作和交付定稿 |
| 可视化报告、根因分析、验证报告、知识沉淀 | 文档站 | `luca-docs` | 适合长期沉淀和对外阅读 |
| 架构图、流程图、时序图、思维导图 | 飞书白板 | `lark-whiteboard` | 默认优先使用白板 DSL 生成图 |
| 结构化表格、看板、数据视图 | 飞书多维表格 | `lark-base` / `lark-sheets` | 适合任务、数据、排期和统计 |

> 注意：拿不准要不要写飞书文档时，先问一句：“这篇需要协作评审吗？”如果需要评论、@人、共同编辑或定稿，优先生成飞书文档。

## 1. 核心原则

### 1.1 结论先行

每份文档开头必须让读者快速知道：

1. 这篇文档解决什么问题。
2. 推荐方案是什么。
3. 当前需要谁做什么。
4. 有哪些风险和待确认事项。

推荐写法：

```md
# XXX 功能技术方案

> 本文档用于说明 XXX 功能的背景、目标、推荐方案、实现设计和上线风险。

## 0. 摘要

| 项目 | 内容 |
|---|---|
| 文档类型 | 技术方案 |
| 当前阶段 | 待评审 |
| 推荐方案 | 方案 B |
| 主要风险 | 接口字段待确认、历史数据兼容 |
| 需要决策 | 是否接受二期再做高级配置 |
```

### 1.2 可视化优先

文档的信息密度应通过图、表、卡片、分栏、Callout 承载，而不是堆砌长段落。

写每一段之前先判断：

| 内容类型 | 优先表达方式 |
|---|---|
| 方案对比 | 表格 / Grid 卡片 |
| 流程说明 | 流程图 / 编号列表 |
| 架构说明 | 白板图 / 模块表 |
| 风险说明 | 风险表 / Warning Callout |
| 结论提醒 | Callout |
| 任务拆解 | 任务表 / Checklist |
| 字段说明 | 表格 |
| 时间安排 | 排期表 / Timeline |

> 规则：如果连续 4 行都是纯文字，就必须判断是否可以拆成表格、列表、Callout 或 Grid 分栏。

### 1.3 面向业务读者

默认读者包括产品、设计、研发、测试、运营、业务方。文档必须减少行内代码和技术黑话。

推荐：

```md
用户上传图片后，系统会先生成预览图，再保存原图地址，避免页面加载过慢。
```

不推荐：

```md
上传后走 presigned url，然后把 object key persist 到 DB，前端 hydrate 时拼 CDN host。
```

如必须使用技术名词，需要补一句解释。

### 1.4 不编造

不能确定的信息必须写成：

```md
待确认：接口是否支持批量查询。
```

不要虚构：

- 负责人
- 日期
- 接口字段
- 数据表
- 线上问题影响量
- 已完成事项
- 测试结果

## 4. 标题层级规范

### 4.1 层级规则

- 一级标题 `#`：文档主标题，用于封面 / 总结。
- 二级标题 `##`：章节标题，用于分层。
- 三级标题 `###`：小节标题，用于细分内容。
- 禁止跳级，例如从 `#` 直接跳到 `###`。
- 标题层级最多使用到 `###`，除非文档非常复杂。

推荐：

```md
# 衣物搭配预览功能技术方案

## 1. 背景与问题

## 2. 方案选择

### 2.1 方案 A：2D 搭配板

### 2.2 方案 B：AI 虚拟试穿
```

不推荐：

```md
# 文档

### 背景

##### 一些内容
```

## 5. 表格规范

### 5.1 什么时候用表格

以下内容优先使用表格：

- 方案对比
- 问题清单
- 接口说明
- 字段说明
- 任务拆解
- 风险评估
- 页面状态
- 排期计划

### 5.2 表格规则

- 表格前必须有文字引导，说明表格内容。
- 列数建议控制在 3 到 6 列。
- 列数较多时，拆成多个小表。
- 不要用纯文本模拟表格。
- 单元格内容保持简短。

推荐：

```md
本次可选方案如下：

| 方案 | 实现方式 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| 方案 A | 2D Canvas 搭配板 | 成本低、上线快 | 不是真实试穿 | 推荐用于 MVP |
| 方案 B | AI 虚拟试穿 | 效果真实 | 成本高、依赖 GPU | 二期考虑 |
```

### 5.3 飞书表格单元格内容写法

当使用 `lark-cli docs +update` 写入飞书文档时，表格单元格内容必须遵守以下规则：

- 单元格 `<td>` / `<th>` 是 HTML 内联内容。
- 单元格内多行内容必须用 `<br/>` 换行。
- 不要在单元格内直接写真实换行，否则会被压成一行。
- 不要在 `<td>` 内塞 `<p>`。
- 单元格内禁止写代码块。
- 类名、方法名、字段名、Trace ID 一律使用纯文本，不要使用 `<code>`。
- 单元格内容应保持简洁。复杂内容拆成独立章节或列表。
- 文本中的 `<`、`>`、`&` 需要转义为 `&lt;`、`&gt;`、`&amp;`。

示例：

```html
<td>第一行<br/>第二行<br/>第三行</td>
```

## 6. 代码块规范

### 6.1 基础规则

- 代码块必须标注语言，例如 `tsx`、`ts`、`bash`、`json`。
- 关键代码行前后需要文字说明。
- 长代码必须分段，每段前说明用途。
- 不要在表格单元格内放代码块。
- 超过 80 行的代码只展示关键片段。

推荐：

```md
文件：`src/components/OutfitPreview.tsx`

下面代码负责渲染搭配预览画布：

```tsx
export function OutfitPreview() {
  return <div>Preview</div>;
}
```
```

不推荐：

```md
下面是所有代码：

```tsx
// 超长代码块
```
```

## 7. Callout 块规范

飞书文档中应使用 Callout 强调重要信息。

### 7.1 可用类型

```md
> [!NOTE]
> 普通备注，用于解释背景或补充信息。
```

```md
> [!TIP]
> 提示或建议，用于给出推荐做法。
```

```md
> [!WARNING]
> 警告或注意事项，用于说明风险。
```

```md
> [!IMPORTANT]
> 重要结论或必须遵守的规则。
```

```md
> [!CAUTION]
> 高风险事项，通常用于上线、数据、安全相关内容。
```

### 7.2 使用场景

| 类型 | 适合内容 |
|---|---|
| NOTE | 背景说明、补充解释 |
| TIP | 推荐做法、经验建议 |
| WARNING | 风险提示、依赖说明 |
| IMPORTANT | 关键结论、必须执行事项 |
| CAUTION | 数据删除、权限、安全、上线风险 |

---

## 8. 分隔线与留白

- 章节之间可以使用 `---` 区分。
- 不要堆砌空行，普通段落之间保留一个空行即可。
- 列表项不要超过 3 层嵌套。
- 一个章节内如果内容超过 3 屏，应拆成多个小节。

---

## 9. 链接规范

- 外部链接必须使用完整 URL。
- 飞书内部链接使用标题引用或飞书文档链接。
- 不要只写“点击这里”。

推荐：

```md
参考文档：[OSS 文件上传方案](https://example.com/docs/oss-upload)
```

不推荐：

```md
参考：点击这里
```

## 10. 图表与可视化规范

### 10.1 默认优先级

默认优先使用 **飞书白板 + DSL** 生成图表。

适合生成：

- 架构图
- 流程图
- 时序图
- 思维导图
- ER 图
- 模块关系图
- 上线流程图
- 事故排查路径图

> 原则：不要因为 Mermaid “省事”就默认使用 Mermaid。节点多、分支多、跨泳道、排布复杂时，应使用飞书白板。

### 10.2 Mermaid 使用限制

仅在同时满足以下条件时允许使用 Mermaid：

| 条件 | 要求 |
|---|---|
| 节点数量 | 小于等于 4 个 |
| 流程结构 | 单线、无分支 |
| 泳道关系 | 无跨泳道 |
| 读者接受度 | 用户明确接受 Mermaid |

适合 Mermaid 的例子：

```mermaid
flowchart LR
  A[上传图片] --> B[去背景]
  B --> C[生成预览]
  C --> D[保存搭配]
```

不适合 Mermaid 的场景：

- 分支很多。
- 节点超过 4 个。
- 多系统交互。
- 需要泳道。
- 需要美观排版。
- 用户明确不接受源码图。

### 10.3 给用户看图的方式

用户不需要审 DSL 源码。正确方式是：

1. 使用 `lark-whiteboard` skill 绘制图。
2. 导出预览图。
3. 给用户看渲染效果。
4. 根据用户反馈调整。
5. 最后写入飞书文档。

不推荐把 DSL 源码直接贴给业务读者。

## 11. “飞书卡片”规范

用户说“卡片”时，通常指以下两类。

| 形式 | 标签 | 用法 | 适用 |
|---|---|---|---|
| 知识卡片 | Callout + emoji / 标签 | 概念解释、提醒、关键结论 | 轻量强调 |
| 对比 / 并列卡片 | Grid 分栏，2 到 3 列 | 方案对比、优缺点、前后对照 | 并列展示 |

### 11.1 知识卡片模板

```md
> [!NOTE]
> **模块定位**
>
> 该模块用于展示用户当前搭配结果，帮助用户快速判断衣服和裤子是否协调。
```

### 11.2 对比卡片模板

```md
| 方案 A：2D 搭配板 | 方案 B：AI 试穿 |
|---|---|
| 成本低，上线快 | 效果真实，但成本高 |
| 适合 MVP | 适合成熟阶段 |
| 不依赖 GPU | 依赖 GPU 服务 |
```

## 13. 常见反例

禁止出现以下模式：

| 反例 | 问题 |
|---|---|
| 整页只有标题和多段纯文字 | 信息密度低，难以快速阅读 |
| 用纯文本列表模拟表格 | 不利于飞书排版和扫描 |
| 复杂图使用 Mermaid 堆在一起 | 节点拥挤，连线交叉，看不清 |
| 概念解释和风险说明直接塞正文 | 重点不突出，应使用 Callout |
| 表格列数过多 | 飞书中横向阅读困难 |
| 单元格内放代码块 | 飞书表格渲染容易异常 |
| 不确定信息写成事实 | 造成误导 |

| 场景 | 页面表现 | 处理方式 |
|---|---|---|
| 加载中 | 显示 loading 或骨架屏 | 禁止重复提交 |
| 空数据 | 显示空状态 | 引导用户新增 |
| 接口异常 | 显示错误提示 | 支持重试 |

## 10. 风险与应对

| 风险 | 影响 | 应对方案 |
|---|---|---|
| 需求变更 | 影响排期 | 变更后重新评估范围 |
| 接口延期 | 阻塞联调 | 先使用 mock 数据开发 |

## 11. 验收标准

1. 用户可以完成核心流程。
2. 异常状态有明确提示。
3. 页面不出现明显控制台报错。
4. 核心流程通过回归测试。

## 12. 执行计划

| 阶段 | 任务 | 产出 | 优先级 |
|---|---|---|---|
| P0 | 完成基础页面 | 可访问页面 | 高 |
